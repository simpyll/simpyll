# Healthcare tools and resources opportunities

All entries are proposals, not released tools. Ranking is an editorial assessment using the current registry, clinical/software interests, feasibility, transparent behavior, maintenance and ability to avoid patient data. No demand metrics or regulatory determinations are claimed. The three strongest next candidates are **NP education cost scenarios**, **a synthetic nursing workflow mapper**, and **a bounded NIHSS educational practice module**. The third is contingent on rights, source verification and independent clinical review; it is not the lowest-risk first build.

## Selection gates and staged rollout

Start with candidate 1, using user-entered assumptions to avoid a data-maintenance platform. Candidate 2 pairs naturally with the existing hospital essay and requires no clinical algorithm. Candidate 3 has clear learning value but must wait for a source/rights/review plan. NP database expansion follows a small curated pilot, not a scraper launched across hundreds of institutions. Clinical-hours trackers and question banks remain ideas: they add persistence/privacy, review, content licensing and maintenance obligations without a small verified corpus today.

Do not create eight overlapping issues from this report. After owner selection, create one bounded implementation brief that identifies intended use, source rights, reviewer, acceptance fixtures, accessibility checks, data handling, release criteria and owner. Do not build these tools under #153.

## Metadata direction: extend the project registry when the first tool is selected

Do not introduce a second tools registry now. `content/projects.json` already owns identity, slug, description/summary, project type, workflow, lifecycle, visibility, live/repository/documentation links and article relationships. A future optional `healthcare` object can be added to that schema and its validator in one product PR; it is a **proposal**, not a currently accepted JSON field.

| Future field | Required meaning |
| --- | --- |
| `intendedUse`, `intendedUsers`, `purpose` | Exact task, audience, and educational/reference/decision-support-candidate classification |
| `assumptions`, `limitations` | Input domain, excluded uses, missing-data behavior and failure modes |
| `sources` | Source URL/identifier, version, relevant algorithm/formula, access date and rights notes |
| `validation` | Unreviewed/engineering-tested/independently-reviewed, reviewer scope, test evidence and unresolved concerns; no implicit clinical approval |
| `review` | Last review date, responsible reviewer/owner, next review due and source-change triggers |
| `dataHandling` | Inputs, storage, logging, third parties, deletion/retention; explicit patient-data policy |
| `safety` | Hazards and controls, classification rationale, clinical-use exclusions and required governance review |
| `versionHistory` | Product version and meaningful changes; link existing source/release records |

Existing project `links` cover repository, live, documentation and supporting articles. Use shared IDs/types and validated canonical paths, never a parallel list of tools claiming a different release status. A future tools destination must filter for actual releases and working destinations, not just public visibility or a case study. Schema tests must reject incomplete clinical metadata, and UI must expose review/limitations at point of use.
