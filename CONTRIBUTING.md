# Contributing to Simpyll

Thanks for your interest in improving Simpyll.

## Getting started

Requires Node.js 24 and npm.

```bash
git clone https://github.com/simpyll/simpyll.git
cd simpyll
npm ci
npm run dev
```

## Before proposing a change

Review [open issues](https://github.com/simpyll/simpyll/issues) and open a focused issue or pull request. Keep changes scoped, describe their motivation and add tests where appropriate.

```bash
npm run lint
npm run build
node --test scripts/prerender.test.mjs
```

For publishing pipeline changes, also run `npm run test:notion` and `npm run test:notion:build`.

Do not commit credentials, private Notion content, or personal access tokens. See [architecture](docs/ARCHITECTURE.md), [deployment](docs/DEPLOYMENT.md) and [Notion publishing](docs/NOTION.md).

## Published MDX validation

Run `npm run validate:content` to check every article under `src/content/blog`.
`npm run build` runs this first, before sitemap generation, compilation, or
prerendering. PR checks, Pages deployment, and the Notion workflow's build before
committing all use this gate. Run `npm run test:content` for its fixture tests;
these also run in all three workflows. No credentials or network requests are
needed for content validation.

Articles use `export const metadata = { ... }`, not YAML frontmatter. Supply
non-empty string `title`, `description`, `category`, and `author` fields, a real
calendar `date` string in `YYYY-MM-DD` format, and a `tags` array of non-empty
strings (the array may be empty). Keep metadata as literal data so it can be
checked without executing article code. Optional `slug` must match the filename.
Use flat filenames with 1–100 lowercase letters/digits separated by single
hyphens and the `.mdx` extension, matching the publisher's slug rules and the
loader's flat glob. Nested articles, symlink articles, and duplicate slugs are
reported rather than silently omitted.

Markdown links/images, reference links/images, and static JSX `href`, `to`,
`src`, and `poster` attributes are checked against the site's routes and files
in `public/`. This includes the string expressions generated by Notion. Use
root-relative destinations such as `/blog/hello-world` and `/images/photo.png`
when possible. Relative destinations resolve against the article's deployed
trailing-slash URL. Public files must resolve inside `public/`; malformed
escapes, encoded separators, traversal above the site root, and unsafe URL
schemes fail validation. Errors include the article path and, for destinations,
the source line and column.

External HTTP(S), protocol-relative URLs, mail, and telephone links are not
fetched. Query strings and fragment identifiers do not affect destination-file
checks; fragment targets are not verified. Dynamic JSX destinations produce a
warning for manual review, and destinations hidden inside custom components or
spreads cannot be statically verified. MDX compilation checks syntax, while the
subsequent Vite build/prerender still checks imports and rendering. The validator
does not execute or sandbox MDX and does not change the Notion publisher, its
ownership manifest, or article contents.
